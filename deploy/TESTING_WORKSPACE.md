# AI Testing Workspace

Open **AI Testing Workspace** in the sidebar, or `/testing-workspace`. The left panel contains the agent conversation, plan review, approvals and incremental results. The right panel streams an isolated Playwright Chromium browser, with clickable takeover and semantic form controls. This is a sequence of JPEG frames, not an iframe or full-desktop VNC session.

## Deployment

The feature adds a third published image, `governance-ai-studio-browser`. The verification workflow tests the worker and builds all three images before publication. Wait for a successful **main** publication before pulling the updated `deploy/hostinger-studio.yml`. Retain the existing Compose project and `mongo_data` volume.

Set the same `BROWSER_WORKER_TOKEN` in the backend and browser service. The worker has no published host port, database credentials, model credentials or storage volume. It runs as a non-root container user, with dropped capabilities, no new privileges, a 2 GB memory limit and a 512 MB shared-memory allocation. Chromium receives a reduced environment rather than inheriting service secrets. ZAP retains its separate 3 GB limit and 1536 MB Java heap.

For repository Compose deployments, copy `.env.example` and set `BROWSER_WORKER_TOKEN`. Use a single backend process/replica and a single private worker. The first version deliberately allows one live browser session per worker. Close a session to release it. Adding replicas requires a durable session/worker registry and distributed admission control, which are not implemented here.

## Workflow

1. Supply the application URL, authorizing owner and approval reference. Confirm this is an authorized isolated test environment.
2. Upload Excel test cases, an SRS, or both. Supported inputs are XLSX, TXT, Markdown, CSV, DOCX and text-based PDF. Up to four files, 2 MB each; up to 500 extracted source statements per session. Spreadsheet formulas are omitted, not evaluated. First nonempty worksheet row is treated as headers; use the included template structure.
3. List any authorized SSO/CDN **origins** in advance, including scheme and port. Other origins are blocked and shown in the browser panel. They are never silently added to scope. Query tokens and credentials are not accepted in the initial URL.
4. Studio's **maker** model proposes use cases and test cases from the masked source register and current browser observation. The selected project's model settings apply, falling back to Studio defaults when no project override exists. Studio's model-call budget, local-only settings and sovereignty restrictions apply. Cloud page/document transmission additionally needs the workspace checkbox. Without a runnable model, reviewable deterministic drafts are created with no fabricated assertions or results.
5. Review the source register, use cases and editable test cards. Edit steps, expected outcome and how each outcome is checked; full JSON editing is available under Advanced. Each case links to source IDs and optionally a use case. Approve the plan explicitly. An oracle specifies the expected visible text or exact URL required for a pass. Missing oracles and non-functional requirements are BLOCKED in this functional workspace.
6. Run the approved tests. The agent observes, proposes bounded browser actions and receives deterministic execution outcomes. Click/fill/select/key interactions require one-time user approval. Approved actions resume the agent. Non-GET/HEAD/OPTIONS application requests independently pause at the worker until the user allows or denies the exact pending request. Approval expires after five minutes.
7. For login/MFA/CAPTCHA, pause and take over. Click an input in the browser image, select **Secure input**, enter the value in the left chat composer and send it. The value is sent to the focused/selected browser field, not to the model, transcript, result or ledger. Click the application control or use **Press Enter**, approve its application request if needed, then resume. The agent does not solve CAPTCHA or supply credentials by itself.
8. Chat instructions pause the agent and steer its next proposal; the configured model can explain the plan and results. Exact chat commands `pause`/`stop` and `resume`/`continue` are deterministic. Scope, approved assertions and approvals cannot be expanded through model text. Use **Regenerate plan** and approve again to change test coverage. Changing an approved plan archives its source links, approval, results and actions in `testing_plan_history` before starting a fresh result set. Owner-authenticated `/sessions/{id}/history` and `/sessions/{id}/history/{version_id}` expose previous plan versions. A finished plan must be approved again before rerunning. Skipping a case records BLOCKED, not PASS.
9. Review each PASS/FAIL/BLOCKED result in the same window, including expected/actual outcome, source links, screenshot hash and ledger reference. Download the JSON report for traceability, unexecuted cases and unmapped source statements.
10. Close the browser when finished. The worker discards cookies and form state. Sessions expire after 30 minutes without browser activity and have a two-hour absolute limit. Reports/evidence remain in MongoDB and are accessible only to their owning governance user.

## Cost and outcome integrity

The existing Studio call ceiling defaults to **2 calls per run**. A plan plus a multi-step execution generally needs a higher ceiling; set an appropriate ceiling in Model Gateway Settings before testing. It is not increased automatically. Budget exhaustion pauses for user attention. Every invocation uses the existing gateway and its hash/latency audit.

Only the approved deterministic browser assertion can produce PASS/FAIL. The model cannot issue a `pass`, `execute`, JavaScript, shell or arbitrary-code action. Each resume is bounded to 15 actions per unfinished case (recent approved actions count toward the case ceiling), 50 cases per plan, and approximately 15 minutes plus the current model/browser operation. Security and performance remain separate Studio runs with their own authorization.

For a simple page check, choose **Direct page check** on the test card and supply its approved page URL and text/URL assertion. Navigation and assertion then run deterministically with no execution-time model calls. This mode verifies that page check only; it cannot claim that a multi-step business workflow ran. Agent-driven workflows use the configured model, with user approval gates. Every result states its verification scope and links to the recorded actions.

## Tested and remaining boundaries

Unit tests cover document provenance, formula omission, plan validation, ownership, cloud consent, shared model budgets, credential handling, handoff and assertion-driven verdicts. Real Chromium integration tests use a disposable local fixture to verify frames/controls, input-value exclusion, assertions, request approval, blocked origins and stale controls. They do not contact third-party sites or require real credentials or an LLM provider.

This is the first bounded browser implementation. It does not establish complete application coverage, CMMI maturity, penetration-test completion or security certification. Iframes, popup/SSO windows, downloads, WebSockets, arbitrary browser scripts, file uploads into the target, multi-tab flows and native OS dialogs are not supported; blocked flows need user review. Same-origin page links and redirects are supported. Input masking is not universal PII redaction: screenshots and visible page text can contain other application data, as stated in the intake consent.

Request-method gates cannot detect an application that mutates data on GET or via browser-only JavaScript state. Use isolated test accounts/data. Origins are resolved to public IPs and pinned through Chromium host resolver rules at session creation; service workers and WebSockets are blocked. These application controls are not a network firewall or protection against a compromised Chromium process. A production deployment needs enforced egress, a hardened browser sandbox/per-run container isolation, retention/deletion controls, TLS, reviewed SSO support and independent security review. No such stronger claim is made by this implementation.

Backend restart marks unfinished sessions interrupted rather than automatically replaying browser actions. Worker restart or expiry returns an explicit browser-unavailable message; create a new session and retain the earlier report. No authentication storage state is written to disk.
